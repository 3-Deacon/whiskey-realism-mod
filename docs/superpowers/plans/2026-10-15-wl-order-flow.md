**Goal:** A W&L career player who is a subordinate receives the orders a Civil War subordinate would: a new order when the situation changes materially (never locked out after first contact), a retreat order that always arrives, orders that ride a courier from the issuing headquarters, and order text that names real places and formations. **Architecture:** One capture point. Every order that vanilla or Whiskey sends to the player goes through `AIBattle.CheckCurrentOrderUpdate` (8233), and a skipping Prefix there (`WlOrderCapturePatch`) takes each new order into a courier queue instead of letting vanilla show it at once. The courier queue delivers it after the issuing headquarters' courier delay, and the delivery is Whiskey's own call back into `CheckCurrentOrderUpdate`. The re-admit policy runs at that delivery, before the call: when vanilla's dedupe would drop an order the policy admits, the delivery empties the slot, calls vanilla, and restores the old order if vanilla still refuses. Whiskey's own battle emitters (#62 and the executor's ancestor dispatch) enqueue directly. The campaign runtime holds its own orders in the same queue type. Pure decisions (re-admit, courier delay, queue, text, type map, compliance gate) sit in the test csproj; runtimes and patches do not.

## Purpose, advantage, measurement

- **Purpose.** Give the subordinate W&L player a working chain of command: orders that keep coming as the battle changes, arrive with realistic delay, say where and why in plain words, and never contradict the army's state.

## Decisions

Each: the problem, the user effect, and the alternative it beat.

- **D1 — One capture point, re-admit at delivery.** *Problem:* the research note's lock-out design (a Postfix that clears the slot and re-calls vanilla after a dropped call) and the courier decision both need to own the moment an order reaches the slot. *Decision:* a skipping Prefix on `CheckCurrentOrderUpdate` captures every new order bound for the player into a courier queue; delivery is Whiskey's own call, and the re-admit policy runs before it (policy → if needed save and empty the slot → call vanilla with the bypass set → restore if the session did not advance). *User effect:* one place decides when and whether an order arrives; vanilla's gates and texts still run at delivery. *Beat:* the note's Postfix re-call (rejected: with every order couriered the Postfix would fire only on Whiskey's own delivery calls, so it would be a second mechanism for the same job; it would also see vanilla's reassigned arguments, 8398-8401).
- **D2 — Couriers off still uses the queue.** With `Enable W&L Order Couriers` off the delay is 0 and the order is delivered at the next delivery pass (≤ 30 frames). The capture runs whenever re-admit or couriers is on; with both off the Prefix passes everything. *Beat:* capture only when couriers are on (rejected: re-admit alone would then need D1's rejected Postfix back).
- **D3 — What is captured.** A call is captured when it reaches vanilla's dedupe (the gate mirror in § Interfaces, `WlOrderCaptureGate`), is not a type-11 refresh (type 11 onto an active 11: vanilla's silent in-place update, `flag4`; emptying the slot would turn it into a new order and a pop-up), and is not type 13 or 14. **13 and 14 pass straight to vanilla:** they report the player's own command's contact state (6800-6809), and a courier from HQ announcing "you are in contact" would arrive after the fact. The user confirmed this exemption ("Keep those two instant (Recommended)"). Retreat (15) is couriered. A call vanilla would drop and the policy would not admit is dropped at capture, as vanilla would (no courier for a no-op).
- **D4 — The re-admit policy (`PlayerOrderReadmitPolicy`, pure).** Given the active order (type, point in 3D, area rotation, age on the doctrine clock, objective own-held, army defensive, `flag2`) and a candidate (type, point in 3D with the terrain height vanilla samples at 8638-8639, rotation, origin), `Decide` first asks `PredictVanilla` (8643 clause by clause, 3D distance as vanilla measures, clause (b) with the 35° rotation test); if vanilla would accept it returns `Admit`. ### The shared row: `DLC_WL.givenorder`

Writers: vanilla (inside `CheckCurrentOrderUpdate`; the EOD clear 47985; the zone-completion clear 123533; scene load 23862/29878; save load 45486), `WlOrderFlowRuntime` (battle delivery transaction, D18's `commanderid`, D20's content) and `WlCampaignDispatchRuntime` (campaign delivery). **Conflict rule:** every Whiskey write happens inside one delivery transaction on the main thread, reads the slot immediately before writing, and writes nothing if the slot's object changed since its read (reference compare); it then puts the entry back (`Requeue`, D8 (d)) and re-evaluates it on the next pass. Two due entries in one pass run one after another, each against the slot the previous one left. Vanilla's own writes between passes always win (they are vanilla's state). A battle entry never delivers while a campaign order is the active object (the scene load clears it at frame 2; an entry seeing a non-battle type in battle discards `cross-scope`). Campaign entries deliver only on the campaign map.

### Entity lifecycles

- **Courier entry.** *Create:* capture, `Emit`, `ShowOrder`, release, follow-up, derived retreat. *Change:* none (immutable once queued). *Unbind:* delivery, discard (superseded, policy drop, unit gone, EOD, command change, overflow, cross-scope, vanilla threw); *Rebind:* `Defer` and a changed slot requeue it. *Delete:* `BattleScope`/`CampaignScope` reset; a campaign entry also leaves the sidecar on delivery. *Migration:* D12 (battle), D11 (campaign sidecar; an entry whose unit no longer resolves after load is discarded `unit-gone`).
- **Order age stamp** (`ActiveSince`, doctrine hours, per session number). *Create:* an accepted delivery stamps its session at the delivery time; the first session the delivery pass sees in a battle (an order present at battle start or after a load) is stamped with infinite age, so D4 treats it as past the hold. *Change:* each new session (one Whiskey did not deliver, e.g. a passed-through 13/14, is stamped when first seen). *Delete:* `BattleScope`.
- **Release latch** (no-contact hysteresis start, rout state). *Create/Change:* each delivery pass. *Delete:* `BattleScope`, or the active order no longer 13.
- **Removal-call stamp** (D13). *Create:* `CheckRemovalOfOrders` Prefix. *Delete:* its Finalizer (call-scoped, also on throw).
- **Capital speed snapshot** (D9 b). Call-scoped: Prefix creates, Finalizer restores and clears.
- **#62 pending signature.** *Create:* `Emit` enqueue. *Unbind:* delivery callback (accepted/attempt) or discard. *Delete:* existing `ClearForBattleBoundary`.
- All references are **latest**: an entry resolves its unit by instance id at delivery (no pinned objects across frames); the issuer position is taken at capture (the courier left then).
