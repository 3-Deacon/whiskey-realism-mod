**Goal:** Implement roadmap stage D (`docs/superpowers/specs/2026-10-15-battle-core-design.md`, binding; it absorbs §A-§C of `2026-10-14-wl-chain-of-command-design.md`). A single `OrderArbiter`/`OrderExecutor` pair becomes the only write path for battle movement, stance, formation, facing and combat behavior. Harmony patches either steer vanilla's own inputs, or call the executor inline through the same guarded pipeline. Patches never submit intents to the arbiter and never write doctrine state.

## Global Constraints

- **Vanilla first.** Before touching code that reads or writes vanilla state, read the full vanilla body and its callers. Cite anchor lines in the file header comment and in the commit message. Code not grounded in the vanilla body is rejected in review.
- **Never throw from a patch.** Every reflection lookup is cached in a static field, wrapped in try/catch, and logs one bounded `OnceLog.Warning`. Restores go in `[HarmonyFinalizer]`.
- **`TelemetryPerf.Scope` on every patch entry.** Wrap every static Prefix/Postfix/Finalizer body in `using (TelemetryPerf.Scope("tactical.patch.<short-name>", TelemetryLayer.Tactical, TelemetryCategory.Performance, 2.0))`. Use 5.0 for heavy paths: the arbiter patch and the snapshot build.
- **Static OnceLog keys.** Never embed an instance id or name in an OnceLog key (13bfeec).
- **Scoped state.** Every static per-battle cache registers `BattleScope.Register("<name>", Reset)` from its static constructor (`Util/ScopedState.cs`). No hand-wired resets.
- **One doctrine clock.** Every doctrine timer reads `TacticalDoctrineTime.NowBattleHours` / `NowBattleSeconds`, which is night-frozen. There is one exception: vanilla's own `lastaistancechangetime` stamp stays on `GameVars.currenttimefromstart`, because vanilla compares it with that clock (4264). Real time is allowed only for telemetry throttles and CPU budgets.
- **All-on config.** Every bool flag defaults `true`, and descriptions state the real default. Rollback is `Tactical Commander Mode = MonitorOnly/Off`. Only BC0 (adds) and BC7 (removes) edit `Plugin.cs`.
- **No dead code.** `python3 -I tools/orphan-sweep.py .` returns 0 findings and `--include-test-only` lists nothing this slice added. `python3 -I tools/config-audit.py .` returns 0 findings. Both must pass at the end of each workstream for the files it touched, and repo-wide at BC7.
- **Tests.** Each workstream owns one test file `tests/WhiskeyRealism.Tests/<Name>Tests.cs` declaring `internal static class <Name>Tests { public static void Run() }`. Harness auto-discovery (parallel Stage B branch) is assumed, so add no `Program.cs` registration line. Add a `<Compile Include>` for every new pure file and remove the entry for every deleted file. Use `TestHarness.AssertEqual/AssertTrue/AssertFalse`. Allocation tests use `GC.GetAllocatedBytesForCurrentThread()` after a warm-up call (pattern: `TelemetryInfraFixTests.cs:118`). Write the failing test first, see it fail, then implement.
- **Pure means no Unity or vanilla types.** Positions are `float X, Z` (Y only where height matters). `CommandTaskType` (Tactical.Operations, pure) is allowed.
- **Exclusive file ownership.** Each workstream edits only its listed files, plus its own test file and csproj lines. Needing another file means stopping and reporting it.
- **Verify before reporting.** Run `./build.sh` (0 errors, 0 warnings) and `dotnet run --project tests/WhiskeyRealism.Tests/WhiskeyRealism.Tests.csproj` (all PASS), and paste the counts. Run `git log --oneline -10 && git status` before each commit. Commit messages follow `feat(battle-core): <summary> [BCn]`, then the anchors, then `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **No new Transpilers.** No new Prefix-skips beyond those listed in the BC5 inventory.

## Spec decisions resolved by this plan

| # | Open point | Decision |
|---|---|---|
| D1 | Threading the snapshot to consumers | `BattleCoreTick.EnsureSnapshot(AIBattle, int alliance)` builds at most once per `(battleKey, alliance, Time.frameCount)`. The coordinator calls it first in `TacticalBattleCoordinatorRuntime.Tick`, which runs from the `TacticalObserverPatch.CheckGlobalAIStrategyPostfix` (vanilla 5866). The arbiter patch at 5870 reuses that object in the same `UpdateAITasks` call. Pure consumers take `BattleSnapshot` as a parameter. Patches read `BattleCore.TryGetSnapshot(alliance, out BattleSnapshot)`, a read-only accessor. Each side has two pooled instances (current and previous) so the executor can compare outcomes against the last tick. |
| D2 | Memo per tick | `BattleSnapshot.TickId` increments per build. Derived per-unit values (closest visible enemy, slice pressure) are computed once by the assembler into pooled arrays, never lazily. `TacticalFrameCache` in `TacticalFogOfWarContact` is deleted, because the snapshot is the memo. |
| D3 | Arbiter tick vs vanilla `UpdateAITasks` (5857-5872) | One Postfix on `AIBattle.AdjustGroupFormations` (5870) at `Priority.Last`. This is the hook #61 uses today, and #61's Postfix is deleted. It runs after vanilla's own movers in the same call: `UpdateMovingTargets` 5862, `CheckFlankMoves` 5867, `AdjustGroupAIStance` 5869, `AdjustGroupFormations` 5870. Whiskey's winning orders are therefore the last macro-cycle write, using a snapshot built at 5866 in the same frame. It is gated by `PostureExecutorBattleGate.Allows` (state ≥ 5, macroai ≠ 3 → `ReleaseForRetreat`, eod, feud instance, player instance unless `ai_vs_ai`) and by `TacticalBattleCoordinator.DrivesOrchestrator`. `CheckForFeudGroupActions` (5871) runs after it and is the feud instance only. |
| D4 | Collecting intents without patches writing mod state | (a) **Producers:** every Whiskey-originated order comes from an `IBattleIntentProducer` run inside the arbiter tick over the snapshot. (b) **Inline steering:** patches that must act inside a vanilla micro call (#56 courier parity, #42 feud replay) build a `BattleOrderIntent` and call `OrderExecutor.ExecuteInline(...)`. That call runs the same guard → chain → validation → pre-check → dedupe → call pipeline. It is refused when a higher-priority claim exists for that group and channel in the arbiter's published claim table, which is read-only to patches. Executor bookkeeping (claims, outcomes, cooldown stamps) is write-path state owned by the executor. It is not doctrine/orchestrator state, so the AGENTS.md "patches READ" rule holds. |
| D5 | Command tree source | Each group's `allattachedunits` (all descendants, 119840+) is scanned once per roster change. A child's direct parent is the containing group with the smallest `allattachedunits.Length`. This needs no `transform.parent` (AGENTS.md rule) and no `GetAttachedUnitsReg` allocation (it uses `Array.Resize` per element). It reproduces vanilla's own direct relation, because `GetAttachedUnitsReg(directonly)` tests `transform.parent == this`. Disagreements with vanilla's `Transform.IsChildOf` ancestry (used by `CheckCurrentOrderUpdate` 8272 and `IsUnitUnderCommander` 91203) are counted and logged once per battle as telemetry. |
| D6 | Queued orders vs the spec's "outcome next tick" | Under `useorderdelay`, `SetWaypoint` queues through `AddToOrderQueue` (91483-91510) but still reaches `SetGroupFormation`/`RegimentSetPath` in the same call (91540/91559, `newpath:false`), and `AddPath` adds the path at once (`regimentpaths++` 130519) with `pathstatus` 0 until the courier arrives (131243-131246). So there is no courier wait to observe and no `Pending` outcome: a move is `Moved` when its targets' moving-unit count rose (at the call or by the next tick) or vanilla took the target (waypoint stamp, step 8), else `Failed` at the next tick (a silent exit; the pre-checked ones never reach the call). (Revised in the BC4 review: the first draft assumed `regimentpaths` stayed 0 until delivery.) |
| D7 | Map bounds clamp (spec says `[1, size−2]`) | Vanilla 131057-131068 clamps **x to [1, sizeX−2] and z to [−sizeZ+2, −1]**, because the battle z axis is negative. `WaypointValidator` uses that rule. It reuses `VanillaMapBounds.ClampXZ` (moved from `CommandPostureExecutor.cs:381`) with a parity test against the vanilla lines. |
| D8 | Ladder vs today's division-play override | The spec ladder is binding: Executor (#61) beats Play. Today the division play overrides the ledger task inside #61 (patch L156-172). After the migration, a division-play order only wins for a child where the posture producer submits no intent on that channel. This behavior change is recorded in the BC5a commit and in `docs/tactical-operations-ledger.md`. |
| D9 | §C dispatch vs existing #62 | `PlayerSubordinateOrderPatch` (#62) already issues the player's own order through `CheckCurrentOrderUpdate`. Both #62 and the executor's §C ancestor dispatch call the one emitter, `TacticalPlayerDispatchRuntime.Emit`. It owns the single `PlayerOrderDedupeState`, moved out of #62. That gives one dedupe for (type, target within 110 m) and no double pop-up. |
| D10 | Charge mechanics (spec §4b) | Vanilla charges only when `combatbehavior == 3 && movementmode == 0 && regimentpaths > 0` (122207). Its target is `unitrange.enemyinrangereg[0]` (122224), which is unsorted (122840) and range-only. Its own strength trigger is `GamePrefs.microaitriggerforcharge`, with weights `weightingfactorsformicroaicharge[0..3]` and radius `GamePrefs.maxchargeradius` (122229-122259). Therefore: (1) behavior 3 is written per **regiment**, never on the group, because micro cycle 6 (5617-5638) re-orders a group whose `combatbehaviorordered != 2`; (2) the doctrine fires only when the regiment is moving and `enemyinrangereg[0]` is the visible target; (3) vanilla's own trigger is not duplicated, and Whiskey's margins are added on top. |
| D11 | Snapshot vs `TacticalUnitObservationAggregate` | `BattleSnapshot` implements `IObservationSource`. `TacticalUnitObservationAggregate(.Runtime)` and its `Shared` singleton are deleted. So are the legacy per-unit objective-record path (`TacticalVisionRuntimeAdapter.BuildObjectiveRecordsFromBattle`) and its flag `EnableSinglePassObjectiveRecords`. |

### Vanilla findings (build 14703111)

- **Force balance** (`CalculateSideStatsAndUpdateAITasks` 84570): `forcebalance = totalforceweighted_own / max(1, totalforceweighted_enemy) × (1 + averagemorale_own − averagemorale_enemy) × (1 + averageexperience_own − averageexperience_enemy)` (84862-84863). `averageexperience` is the mean `groupexperience` of the side's top battle-data groups (84654, divided 84836); `averagemorale` the mean unit morale (84758, 84771, divided 84792). `CheckGlobalAIStrategy` compares it with `forcebalancetriggerdefend / attack / assaultflanking / assaultnoflanking`, each divided by `1 + initiative × influenceofcommanderinitiativeonattackdefendtrigger` (6396-6430; battleprefs 0.7).

The enemy term is the closest enemy group's `unitrange.ownexpinrange` (6039-6042). **Vanilla quirk, not ported:** `ownexpinrange` sums `Experience() × morale` without a strength factor (122751) and divides by `ownstrengthinrange` (122894), so for any real force it is ≈ 0 and the divisor is ≈ `1 − ei`. BC8 uses the blend's intended shape on both sides with a perceived enemy experience.
- **Group averages** (`UpdateGroupStrength`): `grouptraining += GetTraining()` (120473), `groupexperience += Experience()` (120508), both divided by the unit count (120671, 120674).

- **Morale and break** (`UpdateMorale`): a morale drop is amplified by `(2 − Experience()) × overallmoraleinfluenceexp` (128677). `GetUnbearableLossesTrigger` (113359-113404): `num = lerp(unbearablelossesmoraletrigger0, …100, alliance.militaryexperience)`; `num ×= 1 − exp × (1 − influenceexpunbearablelossestrigger)`, `× 1 − GetTraining() × (1 − influencetraining…)`, `× 1 − leadership × (1 − influenceleadership…)`; skirmishers × `unbearablelossestriggerskirmishers`; a non-player alliance × `1 + ((ai_vs_ai ? aicheat_shiftedbonusmoralelosstrigger : 0) + usedcampaignbonusrunning) × aibonus_restoringmorale`; day factor `(lerp(…perdayfactorexp0, …exp100, exp) − 1) × battlepasseddays + 1`; result `min(1, (1 − num) × num4 × num6)`. `Tools.Interpolate` over {0, 1} is an unclamped lerp. ### Fog rule (enemy experience)

Vanilla shows a visible enemy regiment's experience to the player: `UpdateUnitIcon` (121547) returns without drawing unless `isvisible` (121594-121598), `isvisible` is false under `iswithinfog` (127461), and the star block (121832-121852) has no alliance gate: `floor(Experience() × 5)` stars, 0-5, regiments only (a battle group's icon shows 0, 121835-121838). Enemy drill is never shown.

**Decision:** `EnemyObservation.Experience` is the star value the player sees, `TroopQuality.PerceivedExperience(e) = (min(5, max(0, floor(5e))) + 0.5) / 5`, capped at 1 (the bucket midpoint, so the estimate is unbiased; the AI learns no more than the star count). It is written only on Visible probe rows and a Remembered observation keeps the last seen value. Reinforcement columns (groups, unseen) carry none and are left out of every experience mean. Enemy morale, needed by the force balance's `(1 + Δmorale)`, is carried the same way (`EnemyObservation.Morale`, last seen while visible), raw, following the BC6b precedent that reads a visible charge target's morale from its record; vanilla shows the player a 3-band morale alert (121371-121378). Own units are read exactly: `Experience()` and raw `training` for regiments, `groupexperience` / `grouptraining` for groups. The alliance `militaryexperience` proxy is not needed for the enemy (it stays an own-side break-tolerance input).

1. **Snapshot (B).** `UnitRecord.Experience` / `Training` as above, for own and enemy records (enemy records stay perception-only). `PerceptionProbeResult.Experience` / `Morale` columns; `BattlePerception.Update` copies them on visible rows. `BattleSnapshot.PerceivedEnemyQuality` (a `SideQuality`: `Morale`, `Experience`, `Known`; `TroopQuality.PerceivedQuality`, mean over observations, visible weight 1, remembered weight `Confidence01`, reinforcement rows excluded; `Known` false with none). Own means: `TroopQuality.OwnQuality` over alive, active, unrouted combat regiments (the `OwnAverages` filter). Zero allocation preserved (assembler test).
2. **Force balance (C).** `TacticalForceBalanceEvidence` gets own / enemy mean morale and experience; `CurrentRatio = own / enemy × (1 + ΔM) × (1 + ΔE)` (vanilla 84862 shape, sanitized ≥ 0; the no-enemy cases keep their 10 / 1 values). `TacticalReinforcementOpportunityDoctrine.EffectiveAttackThreshold` divides by `1 + initiative × influenceofcommanderinitiativeonattackdefendtrigger` after the parity cap, as vanilla divides its triggers (the evidence already carried the live initiative but `Decide` never read it). 3. **Group stance / odds / sector (D).** `TacticalGroupContactInput` takes an own and an enemy blend; `BuildSector` scales own strength by the own blend and every enemy strength term by the enemy blend. Each blend is vanilla's GetGroupStrength product (6052-6057, `includemorale` and `includeexp`): `(1 − mi + morale × mi) × (1 − ei + experience × ei)` (`TroopQuality.AiDecisionBlend`; mi / ei = `moraleinfluenceonaidecisions` / `expinfluenceonaidecisions`, 54712 / 54714, both 0.25). Own = the group's `groupmorale` (120158 / 120670; `UnitRecord.GroupMorale`) and `groupexperience`; enemy = the closest visible observation's perceived morale and stars (vanilla's closest enemy group, 6039; vanilla's `ownmoraleinrange` is Σ morale × strength / `ownstrengthinrange` (122750 / 122892), whose denominator also adds a group's own `groupstrengthdirect` (122886-122889), so it is not a plain strength-weighted mean; the perceived morale is the blend's intended shape, as for experience), else the side's perceived means (visible plus confidence-weighted remembered), else neutral (1). Call sites: the coordinator's `BuildSectorForGroup` (feeds the GroupStance producer), #44's legacy `BuildSectorAssessments`, the observer's telemetry `BuildPerceivedSector`. `TacticalOddsInput` takes the same two blends for its global odds (own side mean vs perceived mean). `ei` / `mi` are read once per battle (`TroopQualityRuntime`, BattleScope), and so is the rollback flag: a runtime toggle applies from the next battle (the campaign scaling of decision 6 reads the flag on each call).
4. **Withdrawal (E).** The snapshot carries each own regiment's `LossFraction` (LossesAreUnbearable 139829-139843: the smaller of L / (L + strength) and L / (L + strength + the detached regiment's strength), since vanilla routs only when both exceed the trigger, 139832 / 139834-139839) and `BreakLossFraction` = `TroopQuality.BreakLossFraction` (vanilla 113363-113400 from explicit inputs: alliance `militaryexperience`, `Experience()`, raw `training`, commander `GetCommanderLeadership()`, the prefs, battle day). `TacticalMoralePressure`: a unit under fire whose loss fraction has reached `NearBreakShare` (0.8) of its own break point is a `WithdrawalCandidate` (B8 ladder → RearGuard → vanilla's fallback shape), so a veteran, drilled, well-led regiment holds longer than a green one at the same losses. Vanilla's own rout stays authoritative.
5. **Charge (E).** `ChargeInput` gets own/target strength, experience and fatigue and vanilla's weights and trigger (read once per battle); `ChargeDoctrine.ConditionsHold` also requires `TroopQuality.VanillaChargeOdds(…) > microaitriggerforcharge`. The target's experience is its perceived (star) value, its strength/morale/fatigue its visible record (BC6b precedent). Vanilla's check after arming stays the final word; the pre-filter only stops arm → refusal cycles, each of which costs the 1800 battle-s back-off. An already armed regiment is not reverted by the odds (vanilla's check decides it).
6. **Campaign (F).** `CoordinatedOperationOptions.ScaledByCommanderInitiative(initiative, influence)` multiplies `RequiredAttackRatio` and `RequiredReinforceRatio` by `1 + (1 − initiative) × influence` (14250/14281 shape). ## BC9 — reconnaissance and probing

**Branch:** `feat/battle-recon` from `a5cce64` (battle core BC0-BC8 merged). **Goal:** the fog-honest AI (BC2 perception, the contact ledger's intel confidence, the 0.35 action gate) must go and look. Vanilla's battle AI never scouts because it never needs to; with Whiskey's AI fog-honest, a side with nothing actively looking stalls in Hold below the gate or advances blind on scripted objectives. BC9 adds cavalry reconnaissance, reconnaissance in force in the Probe phase, a farther skirmisher screen, and folds in the half-built recon pieces already on `main` (coordinator survey, 2026-10-15).

### Vanilla and W&L model (build 14703111)

- **Omniscient AI, so no scouting.** `forcebalance` is true weighted strength of both sides (`CalculateSideStatsAndUpdateAITasks` 84641-84651, 84862-84863); `GetClosestEnemyUnit` (123760) and `closestenemyunitfar*` read every enemy (`UpdateUnitRangeFast` 122658-122663); `CheckEnemyContact` (117155-117383) stops moves on the true closest enemy; nothing reads the AI-side fog grid `fows[1]` (`docs/vanilla-vision-and-movement.md`). Vanilla has no recon task, role or order.
- **Skirmisher companies (type 3) are accidental scouts.** `CheckSkirmishing` (5343-5406, per AI group from the micro AI) detaches row-0 infantry (`GetRow() == 0`) as companies only while the regiment stands (`regimentpaths <= 0`), the group is in screen (1) or defend (2) or its path is interrupted, morale ≥ `aiminmoraletodeployskirmishers`, out of cover, and no enemy is inside the regiment's fire range (5379-5390). It reattaches them when the group goes to assault, the company's morale drops, it is in melee, the army retreats (macroai 3), the parent moves in screen/defend, or an enemy is within `aimindistancereattachskirmishers` (5354-5363). So a vanilla AI skirmisher screen exists only in front of a **stationary** screen/defend line.
- **`DetachCompany`** (90430-90515) instantiates a copy of the regiment, sets `parentregiment` to the source regiment, parents the copy to the source's transform parent (the brigade) and copies `dlcw_isundercommander` (90477). `DetachUnits` ends with `UpdateUnitList` (90239), so the company is in `completeunitlist`: **detached companies are already own records in the battle snapshot**, with the D5 command parent = the brigade (the coordinator's "excluded from the snapshot" refers to the direct-child probe filter, `BattleSnapshotAssembler.IsDirectChild`, which keeps them out of the command tree's direct children, as vanilla's `GetAttachedUnitsReg(excludeskirmishers)` 119840-119880 does). What the snapshot lacked: the source regiment and a company flag.
- **Skirmisher distance.** A type-3 company links to its parent regiment (113061, re-linked by `CheckNewTargetsOfSkirmishers` 128846-128920 when nothing is in its auto-target range). `GetUnitLinkData` (124208-124390) puts a front link (linkedposition 0) at `unitlinkdistance` (10, unitprefs 1069) + `skirmisherdistance` (20, unitprefs 864) = **30 m** ahead of the parent regiment (the brief's "20 m" is the skirmisher term alone), and `UpdateUnitLink` (124396-124500) re-paths the company there on every `updatecyclelinkingbrigades` cycle while no enemy is inside its fire range (`GetClosestEnemyUnit(firerange) == null`, 124467). `SetWaypoint` clears the link of a type 3/4 unit (91514-91516), so moving a company would only last until vanilla re-links it.
- **Cavalry scout companies (type 4) cannot be steered.** `CheckSkirmishing`'s third block detaches them only in screen stance while the cavalry regiment moves (5395-5405; `DetachmentPossible` 7: not dismounted, 90414). `CheckScoutMovingTargets` (124616-124660, every Regiment update) re-paths a scout to its parent's path target whenever it is more than `distanceformovingtargetsscouts` (5 m, unitprefs 1014) off and stops it when the parent has no path. Decision: **the recon vehicle is a whole cavalry regiment** (unittyp 1); a cavalry regiment moving in a screen-stance brigade also throws out vanilla's own 450 m-sight scout company (maximumlineofsight[4], unitprefs 205).
- **Cavalry groups are linked.** `SeparateUnitsToGroups` (7231-7261) moves cavalry reserves (oob symbol 1) into each objective chain's `screeninggroups` when that chain has infantry (`AreInfantryUnitsInGroup`, 7242); `LinkReservesToLineGroup` (6729-6742) links every screening group behind the centre (linkedposition 2) and `AssignReserves` (7102-7119) links the most suitable one to each unanchored flank (linkedposition 3/1). `UpdateUnitLink` re-lays a linked **group** with `SetGroupFormation` whenever its last waypoint is farther than the recommended distance from the link target, so a group-level recon move is undone at the next link cycle. A regiment move is undone only when its group is re-laid (`SetGroupFormation` 92076-92108), i.e. when vanilla or Whiskey moves or re-forms the group.
- **Contact.** `CheckEnemyContact` stops a moving regiment's AI group within `distancetoenemyforinterruption` (100 m, unitprefs 989) of the closest enemy, **except in screen stance** (`ai_stance != 1`, 117253): a screen-stance unit walks on into contact. The interruption is cancelled beyond `distancetoenemytocancelinterruption` (150 m, unitprefs 991). `CheckFallbackDueToEnemyClose` (128924-129013) pulls a regiment in screen stance (or with combat behaviour 4, evade) back when an enemy is within `minimumdistancetonextenemyunittofallback` (25 m): vanilla's own on-contact give-way for screens. `AdjustCavalryBehavior` (5036-5076) charges weak enemies within `maxdistancecavalryattack` (90 m) only outside screen/defend stance, and mounts a moving dismounted cavalry regiment (5072-5075).
- **Formations.** `AdjustGroupFormations` (5875-5934) gives a settled screen-stance group formation 0 (line; group formation names "Line, Double Line, Successive Lines, Attack Column, March Column", 5883), only when not moving. `CheckFormationChange` (127625-127682) switches a regiment into march column (formation 3) itself for a move longer than `mindistanceformarchcolumn` with no enemy within the interruption distance, and back near the destination. Decision: recon and probe moves carry **no formation intent**; vanilla columns the regiment, and the probe group keeps `CommandFormationCorrection.TargetFormationForTask(Probe)` (its current formation unless march column, then line).
- **Regiment formation 4 is the square** (`firearctype = 2` for `formation == 4`, 118174; four all-round fire arcs, 118262-118270; tooltips_battle 107 "Square — immobile formation to stop a cavalry charge").
- **Unit types.** unitprefs: 0 infantry, 1 cavalry, 2 artillery, 3 skirmishers, 4 scouts, 5 courier (unitprefs 4-225). The mod named 4 `Officer` and 5 `Excluded`; BC9 renames them `Scout` and `Courier` (cavalry follow's "target is an officer" matched scout companies).
- **Weakness screen and blind flanks.** `AdjustGroupAIStance` puts groups in screen only as a weakness fallback (4216, 4221-4278); `CheckFlankMoves` (6247-6311) and `FlankMove` (116929) march to flank positions from true positions, never after a look.
- **W&L.** `PerformAIActionDLCWL` (5101-5116): under the career vanilla's per-unit AI actions (skirmisher detach/reattach, cavalry behaviour, perks) skip a unit under the player's command (`dlcw_isundercommander`) unless the player's own group has an AI stance (≥ 1) and the unit belongs to that AI group (5107-5109), so a W&L player in stance mode gets vanilla's auto-skirmishers. A detached company copies its regiment's `dlcw_isundercommander` (90477), so `PlayerOwnership` marks it `PlayerOwned` like its regiment. `ai_vs_ai` (forced by W&L) runs the player's alliance's AIBattle, so both sides scout; the player's own command never takes part (guard, below).
- **Whiskey on `main` before BC9 (code survey).** `CommandNodeRole.Probe` was never assigned (`CommandNodeOperationsRuntime.MapRole` has no Probe case). The operation director entered Scouting only on `recon-contact` (needs EnemyStrength > 0 and confidence ≥ 0.25, `TacticalDecisionDoctrine.IsReconnaissanceContact`); with no contact at all `Odds(own, 0)` ≥ 1.35 committed the operation (`TacticalOperationDirector.SelectOperation`, "selected"). `BattlePhase.Probe` changed no unit task (only `ArmyReplanTriggers` read it). ### Decisions

1. **Snapshot (pure contract, additive).** `UnitFlags.DetachedCompany` (type 3/4 with a `parentregiment`), `UnitFlags.Mounted` (`mounted >= 1`), `UnitFlags.Linked` (`unitlinkedto != null`); `UnitRecord.ParentRegimentId` (the company's source regiment, 0 otherwise). Field reads in `BattleSnapshotBuilder.Capture`. Own-regiment loops are audited so companies do not newly qualify: the recon candidate filter and the skirmisher push read the flag; withdrawal (`CheckLineFallbacks` 5137 filters by type, the doctrine keeps vanilla's unit filter), fire control (skirmishers are fire-control units as shipped) and charge (infantry type 0 only) are unchanged.
2. **Ledger read API.** `TacticalEnemyContactLedger` keeps its 25 m lateral cells and gains (a) per-entry-point watch stamps (pooled, keyed by the entry point's instance id, positions with them), fed by `ArmyEvidenceBuilder.BuildEnemyVisibleState` where it already computes the watched set (its entry list is pooled, no per-build `List`), and (b) `TryStalestBand` (the current coverage band with the lowest recency, its lateral centre in the ledger's world-anchored frame and the frame heading). The ledger resets its band cells when the frame turns more than 1 degree (`ObserveCoverage`); the entry-point stamps are keyed by instance id and survive the turn (`ObserveEntryPoints`). Recon starts are bounded per hour and per target, so a band reset alone never floods them. `ArmyEvidenceBuilder.ContactLedger(alliance)` becomes an internal read accessor.
3. **Recon planner (pure, `Tactical/Battle/BattleRecon.cs`) is the single owner of "where to look".** Per side, per arbiter tick, on the snapshot and the ledger picture:
   - *Trigger:* no mission running, fewer than `MaxMissionStartsPerHour` (4) starts in the last doctrine hour, and either intel confidence below `TacticalReinforcementOpportunityDoctrine.MinIntelConfidenceForAction` (0.35), a stale enemy entry point, or a stale band.
   - *Target, in order:* the nearest enemy-side entry point not watched for `StaleHours` (1 h; recency 0.5 on the ledger's 2 h scale) or never; then the stalest coverage band below recency 0.5; then, below the gate, straight ahead along the snapshot front axis with no contact ever, or the nearest remembered (no longer visible) enemy after contact (review fix: confidence also falls when contact itself grows old, `contactRecency`, with every band observed and every entry point watched). A target within `TargetRepeatMeters` (100 m) of one picked in the last hour is skipped. The stand point: an entry point is watched by a unit within its line of sight (`MarkVisibleEntryPoints`, maximumlineofsight), so the scout stands `ObservationStandOff` = `distancetoenemytocancelinterruption` (150 m, unitprefs 991; vanilla's own "out of contact" distance, inside cavalry sight 250) short of it, on the line from the scout; a band is observed when an own combat unit stands in it, so the scout goes to the band's lateral centre at the own line's mean forward depth; the forward point is the own line's depth plus `2 × maximumlineofsight[cavalry]` (500 m).
   - *Scout:* an own cavalry regiment (unittyp 1, not a company), alive, active, mounted or not (vanilla mounts a moving cavalry regiment, 5070-5073), standing (no path, no queued order), not routed / marked for rout / on retreat / in melee / garrisoned / permanently detached, not `PlayerOwned`, not `Feud`, morale ≥ `aiminmoraletodeployskirmishers` (vanilla's own bar for sending men out, 5381/5400), no visible enemy within `ObservationStandOff`. Its command parent must be an AI-controlled group that is not moving, has no queued order, is not in assault stance, and did not get a posture move this tick (`PostureTick.Current(s).Groups[parent].Submitted`): the executor's move shield (`BuildMoveShield`) protects only higher-priority claims, so a Support recon move would be re-pathed by its brigade's Executor move — candidate selection is the protection. The closest qualifying regiment to the stand point wins.
   - *Safety:* never toward a visible superior enemy — the stand point is rejected when a visible enemy whose strength is at least the scout's lies within `ObservationStandOff` of it or within `CorridorMeters` (= the 100 m interruption distance) of the straight path.
   - *Mission (state on the doctrine clock, BattleScope store, advanced only on executor outcomes, BC6b pattern):* `Outbound` — a Move intent (Support, `IntentSource.Recon`, task Scout, by courier `UseOrderDelay` as vanilla AI moves go) re-submitted each tick (the executor dedupes it); confirmed only when `TryGetLastOutcome(scout, Move)` is Issued by Recon at or after the submission, else the mission ends (fail closed). `Observe` on arrival (within `OrderArbiter.DedupeMeters` of the stand point or standing after a confirmed move) or on first sight of an enemy within `ObservationStandOff` (a `Stop` intent then); dwell `ObserveDwellHours` (0.05 h) so the heavy evidence pass stamps the ground. `Return` — a Move to the scout's layout slot in its brigade (`LeafSlotTarget`, the shipped #61 slot rule), else to its brigade's position; done within 60 m. Contact: a visible enemy at least as strong within the interruption distance ends the outbound or observe leg early into `Return`; fire makes it the Withdrawal producer's (Safety beats Support), whose move ends the mission (`Recalled`). A scout whose last waypoint vanilla moved off ours (a group re-lay) is `Recalled`. A mission ends after `MaxMissionHours` (0.5 h) whatever its leg.
   - *Look points for Scout/Probe tasks:* `BattleRecon.LookPoint(s, group)` = the group's position advanced `ProbeAdvanceMeters` = maximumlineofsight[infantry] (200 m, unitprefs 29: one sight depth further) along the snapshot front axis, rejected toward a visible superior enemy like the scout's. `PostureTargets.TryResolve` takes the target of a Scout or Probe task from it before the line-planner/objective fallback (the GT recon "by bounds" advance, now a bounded one); with the BC9 flag off the shipped objective stand-off applies.
4. **Reconnaissance in force (probe nomination).** In `BattlePhase.Probe`, for a side that is not the battle's Defender (`ArmyPostureInputsRuntime.SideDefending`), the planner nominates per front band (snapshot front axis, 5 bands) with no visible enemy one AI-pool group: a brigade when the band has one, else the smallest group; not moving, no queued order, not linked (`UnitFlags.Linked`: vanilla's own link would re-lay it), not routed, no player-owned unit in its subtree, not artillery-only, not in assault. At most one start per band per doctrine hour (`MaxProbeStartsPerBandPerHour` 1). A nomination ends on visible contact (any visible enemy within maximumlineofsight[infantry] of the group: the recon producer then submits one `Stop` at Support for it, because a screen-stance group does not stop itself, 117253), on arrival, when the side leaves the Probe phase, or after `MaxProbeHours` (0.25 h); what follows the end is decision 13. It is consumed by `PosturePipeline` as a task rewrite — role `CommandNodeRole.Probe`, task `Probe`, target the nomination's look point — so the posture producer issues it at Executor priority with the mapper's screen stance (`TacticalCommandTaskToStanceMapper`: Probe → 1). The Probe role is thus assigned by the probe rewrite, not by `CommandNodeOperationsRuntime.MapRole` (the allocator's `DirectChildRole` has no Probe).
5. **Director: no contact means scouting.** `TacticalOperationDirector.SelectOperation`: a primary objective with no enemy strength (`NoUsableContact` / zero-enemy `UnreliableContact`) selects `Scouting` ("no-contact-scout"), never `Committed` on `Odds(own, 0)`. `CommandDoctrineAssignment.ResolveTask` gives the recon tasks (`ReconnaissanceTaskFor`) in Scouting also without contact, except for `DefensiveNetwork` / `DelayAndFallback` shapes (a defender is not sent forward). Consequence: `OperationMacroAi(Scouting) = -1` leaves the side's macro opinion to vanilla during the search, as it did for `recon-contact`. Existing director tests that asserted the commit on zero enemy are updated with this reason.
6. **GT recon doctrine.** The cavalry branch (any cavalry in the subtree → group Scout) is deleted: regiment scouting is the recon producer's. Attack tasks without a visible enemy become Probe (Screen for screening roles), aimed by the look point. For a Defender the stance guard (decision 12) runs after this, with or without a visible enemy: Probe → Screen, Attack/Support/Fix → HoldObjective.
7. **Cavalry follow and fire control.** `targetInSquare` = the visible target's own record in regiment formation 4 (118174; BC6b precedent for reading a visible target's record); `targetIsOfficer` = a command group or a courier (unittyp > 13 or 5), not a scout company; `targetHidden` (structurally false on a closest-visible target), `leaderAllowsCharge` (constant true) and `atFollowLocation` (unread) are deleted from the input. Fire control passes the snapshot's `Mounted`, so the cavalry screen-evade branch (behaviour 4, `CheckFallbackDueToEnemyClose`'s give-way, 128955) is live.
8. **Facing.** A Screen / Probe / GuardFlank brigade with no visible threat faces the stalest unwatched enemy entry point (`TacticalFacingThreatSource.Entry`, never urgent); `RecentFire` and `Objective` are deleted (no producer). The facing pulse submits it through `PostureIntentPlan.SubmitBrigadePulse`, whose group-facing gate `CommandFormationCorrection.ShouldFaceThreat(task, source)` accepts the Entry source for Screen and Probe (GuardFlank already faced threats). Regiments: on a clean subtree the group facing turns them; under a brigade with a detached or player-owned descendant each regiment with nothing visible takes the brigade's Entry bearing (the doctrine does not apply the fire-range gate to an entry point). Every other task (HoldObjective, ReserveWait, Consolidate, FixEnemy, Delay, HoldChoke, FallBackToLine) is refused the Entry source (`no-threat-bearing`) and keeps its front-axis facing with no new write, as before BC9. The Entry source also opens the pulse's formation channel for a Screen/Probe brigade, whose target (`TargetFormationForTask`: a march column goes to line, else the current formation) is the posture pipeline's own for these tasks.
9. **Skirmisher screen distance (`SkirmisherScreenDistancePatch`, ordinal assigned at merge; Postfix on `Regiment.GetUnitLinkData`).** Vanilla re-links companies every cycle (124467), so Whiskey steers that input instead of fighting it with moves: for an AI type-3 company on a front link whose command group is in screen stance (or attack stance while moving), with an empty own range list (`FirstEnemyInRangeId == 0`), not in melee and no visible enemy within `distancetoenemytocancelinterruption` + the push, the returned link target is moved forward along the link rotation to `distancetoenemyforinterruption` (100 m, unitprefs 989) ahead of the parent: the distance at which vanilla stops a moving line on contact, so the skirmish line meets the enemy first and, with its 250 m sight (unitprefs 161), sees 350 m past the line (the line's own 200 m sight, unitprefs 29). The result's distance fields are recomputed from the new point exactly as `GetUnitLinkData` computes them (124370-124386), so `UpdateUnitLink`'s gates see a consistent record. On contact the condition fails and vanilla's 30 m returns by itself. Result override of vanilla's own input (no Prefix-skip, no write call, no persisted field: `linkedoffset` is saved with the unit, 73773, so it is not used); guarded by `TacticalWriteGuard.CanWrite(Regiment)` (W&L player companies untouched), Commander Mode Active, the BC9 flag.
10. **Producer and priority.** `Recon` (`ReconIntentProducer`, Support) joins `BattleProducerRegistry.Order` after `DivisionPlay` (it reads the posture producer's per-group record of this tick) and before `ReserveRelease`: 12 producers. Support is right: recon yields to every doctrine move of the same unit; its protection is the candidate filter above. `IntentSource.Recon` is appended (no renumbering).

Off = the shipped objective stand-off for Scout/Probe and no recon moves. The director's no-contact rule and its Defender rule, the GT recon cavalry-branch deletion and Defender screen, and the cavalry-follow / fire-control input fixes are bug fixes and are not behind the flag.
12. **Defender stance (integrator decisions, review rounds 1 and 2).** A Defender side (vanilla `GetBattleType` 2) never gets reconnaissance in force, a Probe task or an attack-stance task (`AttackObjective`, `SupportAttack`, `FixEnemy`: attack stance 3 in `TacticalCommandTaskToStanceMapper`), as AGENTS.md's "a Defender never gets attack doctrine"; it still screens and scouts with the recon producer's cavalry (information-gathering, not an attack). One stance: `ArmyOrchestrator.CurrentBattleStance`, read by `ArmyEvidenceBuilder.ReadBattleStance` (GetBattleType without the readiness tie-break) and refreshed by `ArmyPostureInputsRuntime.Refresh` on every coordinator tick before its `Enable Tactical Reinforcement Opportunity Doctrine` gate (`RefreshPostureInputs` runs before `DriveOperationsLedger`, so the ledger sees this tick's stance). The rule holds on every path: (a) the director (`TacticalOperationDirectorInput.WithStance`, from `StoreDoctrineForCommandStates`) passes every decision through `ForDefender`: once an objective is selected, any shape but `DefensiveNetwork` / `DelayAndFallback` becomes `DefensiveNetwork` and a `Committed` / `Exploiting` phase becomes `Forming` (reasons `defender-screen` in Scouting, `defender-hold` otherwise), so no new selection, earlier commit, downgrade, commit window or hysteresis leaves a Defender in an offensive shape; (b) `TacticalDecisionDoctrine.TaskForStance` is the final guard of every task assignment: `CommandDoctrineAssignment.Build` (any shape, any phase), the GT recon doctrine (with or without a visible enemy), the posture pipeline after all its rewrites (GT recon, cavalry follow, local emergency, opportunity override; the division play runs through the same pipeline) and the leaf cascade; Probe → Screen, Attack/Support/Fix → HoldObjective, everything else unchanged; (c) the probe nomination reads the same stance (decision 4). Out of scope (not task assignments): the #45 group-stance scorer and the BC6 charge doctrine keep their shipped stance handling.
13. **After a probe (integrator decision).** A probe that ends with a visible enemy at least as strong within one infantry sight depth (strength ≥ the group's, as the look point's safety) is over: the group falls back to its ledger task, as before. Any other end (weaker contact, arrival, `MaxProbeHours`) leaves a hold: the group holds the ground it gained (its position when the probe ended; on arrival the probe point) until the ledger reassigns it. `ReconMemory` keeps the hold in a grow-only store with one slot per holding group (a new hold never takes another group's slot; at most one hold per own group, so it stops growing at the roster) (position, the probe's advance direction and the posture task the group had when nominated, `ReconPicture.PostureTask` from `PostureTick`'s group record: the posture producer runs before Recon); the posture pipeline asks `ReconIntentProducer.TryHold` with its final task and drops a posture move whose target lies more than the arbiter's dedupe radius (60 m) behind the held point along the advance (`BattleRecon.HoldBlocks`): no intent, the group stands (a dropped move also drops that tick's stance intent, which the posture executor sends with the move, so a held group usually keeps the probe's screen stance until a posture decision changes stance on its own); forward and along-the-line targets go (a Probe/Scout task keeps advancing by bounds), and a break-off, fallback or recovery keeps its own target. No direct write: the hold only withholds the posture producer's own move intents. The hold ends when the group's posture task differs from the nomination's (the ledger reassigned it, or an emergency/opportunity rewrite), the group is gone, a visible enemy at least as strong comes within one infantry sight depth, a new probe nominates the group, or the flag is turned off. A phase end, a group lost and a Defender flip during the probe end it without a hold.
